# 08. 시연 녹화 (3-2)

내가 손으로 블록을 집어 목표에 놓는 시연을 녹화한다. **이미지는 저장하지 않고 "상태"(관절 각도, 모터 목표, 블록 위치)만 30Hz로 저장한다.** 학습용 이미지는 3-3에서 저장된 상태로 다시 그린다(실시간 렌더링이 약 54ms라 30fps 녹화가 안 되기 때문). 웹캠 영상은 저장하지도 전송하지도 않는다.

## 사용법

서버와 웹은 내가 직접 띄운다.

```bash
cd ~/handover && MUJOCO_GL=egl server/.venv/bin/python -m server.app            # 서버 (먼저)
cd ~/handover/web && npm run dev -- --host 127.0.0.1 --port 3007 --strictPort   # 웹. Ports에서 3007만 Private 전달 → http://localhost:3007
```

화면의 "시연 녹화" 상자:

| 버튼 | 하는 일 | 눌릴 수 있을 때 |
|---|---|---|
| 블록 리셋(다음 시드) | 팔을 올리고(집게 열림) 다음 시드 위치에 블록을 놓는다 | 녹화 중이 아닐 때 |
| 녹화 시작 | 에피소드 녹화를 시작한다 | **리셋 직후에만** |
| 끝: 성공 / 끝: 실패 | 내가 정한 결과로 저장한다 | 녹화 중 |
| 취소(버리기) | 저장하지 않고 버린다 | 녹화 중 |
| 마지막 에피소드 삭제 | 가장 최근 저장본을 지운다(두 번 눌러야 지움) | 저장된 것이 있고 녹화 중이 아닐 때 |

- 표시: 녹화 중 여부, 경과 시간(최대 60초), 기록한 틱 수, 지금 시드/다음 시드, 저장된 성공/실패 수, **정지 구간 비율**, **"성공 조건 달성"**, 마지막 저장, 틱 간격.
- 최대 길이(60초, `RECORD_MAX_S`)를 넘으면 **실패로 자동 종료하고 저장**하며 안내가 뜬다.
- 저장이 실패하면(디스크 가득 등) 빨간 안내가 뜨고, 그 에피소드는 성공/실패 수에 **넣지 않는다**(데이터는 사라지고 다시 시도하는 기능은 없다).
- 녹화 중에 마우스로 화면을 돌려도 괜찮다. 저장되는 것은 상태 숫자라서 학습 카메라(`RECORD_CAMERA_*`)와 상관없다.
- 서버를 끄면 녹화 중이던 것은 버려진다(저장되지 않는다).

## 시연 20개 찍는 절차

1. 서버와 웹을 띄우고 카메라를 켠다. 손을 보이면 로봇이 따라오는지 한 번 확인한다.
2. **"블록 리셋"** → 팔이 올라가고 블록이 시드 0 위치에 놓인다. 상자에 "준비됨: 시드 0"이 뜬다.
3. 손을 보이고 로봇이 따라오는 것을 확인한 뒤 **"녹화 시작"**.
4. 블록 양옆에 먼저 맞추고 → 내려서 집고 → 목표(초록)까지 옮겨 → 내려놓고 집게를 연다.
5. 집게를 연 채 **0.5초 가만히 둔다.** 초록 띠 "성공 조건 달성"이 뜨면 **"끝: 성공"**. 안 뜨는데 성공이라고 판단하면 그래도 누를 수 있다(자동 판정과 다르면 둘 다 기록된다).
6. 중간에 떨어뜨리거나 망설였으면 **"취소(버리기)"**(저장 안 됨, 시드 번호만 건너뜀). 끝까지 해서 실패한 것을 기록으로 남기고 싶으면 "끝: 실패".
7. 실수로 저장했으면 **"마지막 에피소드 삭제"**(두 번 누름). 가장 최근 것만 지울 수 있다.
8. 2번으로 돌아가 반복한다. 매번 **리셋부터** 해야 시작 버튼이 켜진다.
9. 성공이 20개가 되면 끝. 확인:
   ```bash
   cd ~/handover && ls data/raw | wc -l                           # 에피소드 N개면 파일은 2N개(npz + json)
   grep -h '"success"' data/raw/*.json | sort | uniq -c           # 성공/실패 개수
   grep -h '"still_ratio"' data/raw/*.json                        # 에피소드별 정지 구간 비율
   ```
   시드는 0부터 순서대로 쓴다(리셋만 하고 녹화하지 않으면 번호가 건너뛴다). 시연 시드 0~99를 다 쓰면 리셋이 거절된다.

"성공 20개만 학습에 쓸지, 실패도 같이 쓸지"는 3-3에서 정한다(제안: 학습은 `success == true`만, 실패 에피소드는 실패 유형 분석용). 저장 파일에는 성공/실패가 모두 남는다.

## 시연 20개를 잘 찍는 요령

- **블록 양옆에 먼저 맞추고 내리기.** 열린 집게가 블록 윗면에 얹히면 블록을 밀어 버린다. 좌우·앞뒤를 블록 양옆에 맞춘 다음에 ↓로 내린다.
- **한 번에 집어서 옮기기.** 집었다 놓았다 다시 집는 동작은 학습에 나쁜 예가 된다. 한 번에 집어서 쭉 옮긴다. 놓친 것은 "취소"하고 다시 찍는다.
- **망설이지 않기.** 손이 멈춰 있거나 화면 밖에 나가 있으면 로봇이 서 있는 구간이 길어진다. 화면의 **정지 구간 비율**이 50%를 넘거나 가장 긴 정지가 3초를 넘으면 노란 경고가 뜬다(임시 기준, 20개 찍어 보고 조정). 그럴 땐 "취소"하고 다시 찍는다.
- **실패하면 취소.** 블록을 떨어뜨렸거나 이상한 데 놓았다면 "취소(버리기)". 억지로 이어서 성공시키지 않는다.
- **손을 화면 밖으로 빼지 않기.** 가장자리 근처(빨간 테두리)에서는 중앙에서 다시 넣으면 이어서 움직인다. 녹화 시작 전에 손을 먼저 보이고 따라오는 것을 확인한 뒤 시작한다.
- **같은 속도, 같은 방식으로.** 매번 비슷한 경로(위로 접근 → 양옆 맞춤 → 내림 → 집기 → 들기 → 이동 → 내림 → 열기)로 한다. 너무 빠르게 휘두르지 않는다.
- **놓은 뒤 집게를 열고 0.5초는 가만히.** 성공 조건은 "블록이 목표 안 + 바닥 + 집게 열림"이 0.5초 이상 유지되는 것이다.
- **리셋 뒤에 블록을 건드리지 않기.** 리셋 직후 블록이 시드 위치에서 1cm 넘게 벗어나면 녹화 시작이 거절된다.
- 높이는 키보드(↑↓, W/S, Shift = 천천히)다. 블록 근처에서는 Shift로 천천히 내린다.
- 한 번에 오래 찍지 말고 중간에 쉬어도 된다. 다음 번호는 저장된 에피소드를 보고 이어서 정해진다(서버를 껐다 켜도 같다).

## 저장 형식

위치 `data/raw/`(`.gitignore`의 `data/`에 걸려 git에 올라가지 않는다). 첫 저장 때 폴더가 만들어진다. 에피소드 하나는 파일 두 개다.

```
data/raw/episode_000012.npz     배열 (numpy만으로 읽힘, pickle 불필요)
data/raw/episode_000012.json    메타 (사람이 읽기 쉬움)
```

**형식을 npz + json으로 고른 이유:** 서버에 새 패키지가 필요 없고(numpy만), 학습 환경(`train/.venv`)에서도 `np.load(..., allow_pickle=False)`로 읽는다. parquet은 pyarrow가 필요해서 쓰지 않았다. json은 목록을 훑을 때 npz를 열지 않아도 된다. 파일은 임시 이름으로 쓴 뒤 바꿔치기하고, **npz → json 순서로 쓴다. json이 있어야 저장된 것**으로 친다(쓰다 끊긴 파일은 무시된다). 이미지·영상 배열은 없다.

**npz 배열** (길이 T = 틱 수, 모두 float64이고 `is_intervention`만 bool):

| 이름 | shape | 내용 |
|---|---|---|
| `sim_time_s` | (T,) | 샘플을 찍은 시뮬레이션 시각(s) |
| `qpos` | (T, 13) | 전체 관절 위치. 순서: 팔 6개(shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, **gripper**) rad, 블록 x, y, z (m), 블록 회전 쿼터니언 w, x, y, z |
| `ctrl` | (T, 6) | 모터 목표(rad), 팔 6개와 같은 순서 |
| `is_intervention` | (T,) | 사람이 넘겨받은 구간 표시. 이번에는 전부 `False`(4단계용 자리) |

**json 메타** (주요 항목):

| 키 | 뜻 |
|---|---|
| `episode_index`, `seed`, `source` | 에피소드 번호, 시드, `"demo"` |
| `success`, `end_reason` | 내가 정한 최종 결과, 끝난 이유(`stop_success` / `stop_fail` / `max_length`) |
| `auto_success` | 자동 판정: `ever`(한 번이라도 유지 달성), `first_sim_time_s`, `at_end`. 내 결과와 다르면 `success_differs_from_auto: true` |
| `n_ticks`, `duration_s`, `fps`, `sim_timestep_s` | 샘플 수, 길이, 30, 0.005 |
| `still_ratio`, `still_longest_s`, `still_ctrl_delta_rad` | **정지 구간 비율**, 가장 긴 연속 정지(s), 정지로 보는 기준(rad) |
| `block_start_m`, `target_m` | 블록 시작 위치 x, y, z / 목표 x, y |
| `created_at` | 만든 시각(타임존 포함) |
| `scene_sha256`, `robot_model_sha256` | `sim/scene.xml`과 로봇 모델(`so101.xml`)의 SHA-256. 3-3에서 같은 장면인지 확인한다 |
| `config_sha256`, `config` | `server/config.py`의 대문자 설정값 전체와 그 해시(경로 값 제외) |
| `record_camera`, `qpos_layout`, `joint_names`, `mujoco_version`, `format_version` | 학습 카메라 값, qpos 순서, 버전 |

크기: 30초 에피소드(900샘플)가 npz 약 70~105KB + json 약 5.5KB(실측 6개: 67,528 ~ 104,342 bytes, 평균 약 89KB, 움직임이 많을수록 큼). 100개여도 약 10MB.

## 틱 정렬 규칙 (state와 action이 같은 순간)

샘플 k는 **한 순간(물리 스텝 직전)에 `qpos`와 `ctrl`을 같은 호출에서 한꺼번에 복사**한 것이다(`server/recorder.py` 맨 위 주석, 호출 위치는 `server/sim_worker.py`의 물리 루프).

```
샘플 k (시각 t_k, mj_step 직전):
  qpos[k] = data.qpos 전체 13개          → 학습 observation.state[k] = qpos[k][:6]   (행동을 적용하기 전 팔 관절 6개)
  ctrl[k] = data.ctrl[:6] (지금 적용 중)  → 학습 action[k]            = ctrl[k]
  이미지[k]                              → 3-3에서 qpos[k] 13개 전체로 다시 그림(블록 포함)
  이 ctrl이 만든 효과는 qpos[k+1]부터 보인다.
```

- `mj_step` 뒤의 값(`SimWorker.snapshot`)은 쓰지 않는다. 같은 호출에서 복사하므로 한 샘플 어긋날 수 없다.
- 테스트(`server/tests/test_recorder.py`)가 실제 MuJoCo로 독립된 기준 실행의 같은 스텝 직전 값과 **정확히 같은지**(`array_equal`), ctrl이 바뀐 샘플의 qpos가 아직 그 영향을 받기 전인지 확인한다. 일부러 `on_step`을 `mj_step` 뒤에 부르게 바꾸면 60개 샘플이 모두 불일치로 걸리는 것도 확인했다.

### 시간 격자 — 평가도 같은 격자로 돌려야 한다

모델 `timestep`은 0.005초라서 1/30초(33.3ms)가 스텝의 정수 배가 아니다. 그래서 샘플 k를 **시뮬레이션 시간 t₀ + k/30에 가장 가까운 물리 스텝**에서 찍는다(`server/grid.py`, 순수 함수).

```
스텝 번호 s_k = ceil(k / (fps × timestep) − 0.5)       t₀(첫 샘플 시각)에서 몇 스텝 뒤인가
fps 30, timestep 0.005 → s = 0, 7, 13, 20, 27, 33, 40, …  (간격 35, 30, 35, 35, 30, 35 ms 반복)
```

- 격자와의 차이는 최대 2.5ms(실제 1.67ms). 실제 샘플 간격은 30ms와 35ms가 번갈아 나온다(평균 33.33ms). 정확한 시각은 `sim_time_s`에 있다.
- 틱 간격(벽시계)과는 상관없다. 화면 렌더링 때문에 틱이 늘어져도 샘플은 시뮬레이션 시간 격자에 찍힌다.
- **3-4 평가 루프도 같은 격자를 써야 한다.** 학습할 때 본 "정책을 부르는 간격"(30ms/35ms 교대)과 평가 때 간격이 다르면 학습 조건과 어긋난다.

```python
from server.grid import grid_step_indices
steps = grid_step_indices(n_policy_calls + 1, config.RECORD_FPS, model.opt.timestep)
# k번째 정책 호출 뒤에 steps[k+1] - steps[k] 개(6 또는 7개)의 mj_step을 진행하고 k+1번째 관측을 만든다.
# 정책을 부르기 직전의 qpos[:6]가 observation.state, 정책 출력이 data.ctrl[:6](action)이다.
```

3-3(데이터셋 변환)은 저장된 샘플을 그대로 쓰고(`timestamp = frame_index / 30`로 기록하면 최대 1.67ms 어긋남), 필요하면 `sim_time_s`로 어긋남을 확인한다.

## 시드

- 시연 시드 **0~99**(`DEMO_SEED_RANGE = (0, 100)`), 평가 시드 **1000~1049**(`EVAL_SEED_RANGE = (1000, 1050)`). 겹치지 않는다(`server/tests/test_seeds.py`). 범위는 `server/config.py`.
- 시드 → 블록 위치: `server/seeds.py`의 `block_xy_for_seed(seed)`. 같은 시드는 항상 같은 위치다(numpy `default_rng(seed)`). 영역은 x 0.19~0.25, y -0.10~0.04 m, 블록은 바닥 위(z 0.015)에 **회전 없이** 놓는다. 목표(초록, 0.20, 0.12)는 고정이다.
- 화면의 리셋 버튼은 시연 시드만 쓴다. 평가 시드는 3-4의 코드가 `block_xy_for_seed(1000 + i)`로 쓴다.
- **다음 시드**: 서버를 켤 때 저장된 시연 에피소드의 가장 큰 시드 + 1(없으면 0). 리셋을 누를 때마다 1씩 늘고 취소해도 되돌리지 않는다(번호가 건너뛸 수 있다). 마지막 에피소드를 지우면 다시 계산된다.
- **영역 확인** (`server/spawn_check.py`): 영역을 사방 2cm 넓힌 격자 209점에서 IK가 모두 풀렸다(블록 높이 z=0.015와 접근 높이 z=0.08, 최대 오차 0.99mm, 집게 최대 기울기 5.4°). 네 모서리와 중앙에서 자동 집기로 5cm 들어 올리는 데 모두 성공했다(들린 높이 42.8~45.3mm). 기본 영역을 줄일 필요가 없었다. 목표 위 놓기 자세(0.20, 0.12, 0.03)도 풀린다.

## 블록 리셋 순서

블록이 집게에 끼지 않도록 **팔이 먼저 비켜난 다음에 블록을 놓는다**(`server/reset.py`, `server/control.py`).

1. 손·키보드 높이 입력을 무시하고 이전 목표·필터·집게 상태를 지운다.
2. 팔을 home 자세(위로 세움)와 **열린 집게(0.9 rad)** 로 보낸다(평소와 같은 속도 제한). 이 자세의 집게 끝은 x 0.03, z 0.35 m라 블록 영역과 멀다.
3. 모든 관절이 목표에서 0.05 rad 안으로 0.2초 유지되면 도착. **4초 안에 못 가면 블록을 건드리지 않고 중단**하고 오류로 알린다.
4. 시뮬레이션 스레드가 블록을 시드 위치로 옮기고 속도를 0으로 만든다. 그 자리에서 블록이 바닥 말고 다른 것과 닿으면 놓지 않고 되돌린 뒤 실패로 알린다.
5. 0.3초 뒤 블록이 시드 위치에 있는지 확인하고(3mm) "준비됨". 이후 손이 3프레임 연속 보이면 처음 서버를 켰을 때처럼 작업 상자 중심에서 시작한다.

녹화 중에는 리셋이 거절된다. 리셋 후 `block_ready`는 새 리셋이 진행되는 동안 꺼져 있고, 녹화를 시작하면 꺼진다.

## 성공 자동 판정 (3-4 평가도 같은 함수)

`server/success.py`. 조건(모두 만족)이 **0.5초(시뮬레이션 시간) 이상 계속** 맞으면 달성. 값은 `server/config.py`.

| 조건 | 기준 | 경계 |
|---|---|---|
| 블록 중심 xy가 목표 중심에서 | 반변 0.025 + 여유 0.005 = **0.03 m 안쪽**(`TARGET_*`, `SUCCESS_XY_MARGIN_M`) | 경계 포함 |
| 블록 중심 높이 | **z < 0.02 m**(`SUCCESS_BLOCK_Z_MAX_M`, 바닥 위 중심은 0.015) | 경계 제외 |
| 집게 실제 각도(qpos) | **≥ 0.5 rad**(`SUCCESS_GRIPPER_OPEN_MIN_RAD`) | 경계 포함 |
| 유지 시간 | **≥ 0.5 s**(`SUCCESS_HOLD_S`) | 포함. 한 번 끊기면 처음부터 다시 센다 |

- 집게 기준 0.5는 실측 사이에 있다: 블록을 집은 채일 때 집게 각도 약 0.17 rad, 열림 목표 0.9 rad(`spawn_check`).
- `is_success(block_m, gripper_rad)`가 한 순간의 조건, `SuccessHold`가 유지 시간, `success_over_time(sim_time_s, qpos)`가 저장된 에피소드를 다시 판정한다.
- 목표 위치·크기가 `scene.xml`의 `target`과 같은지는 테스트가 확인한다.
- 녹화 중 달성하면 화면에 "성공 조건 달성"이 뜬다. **최종 성공은 내가 누른 버튼**이고, 자동 판정(`ever`, `first_sim_time_s`, `at_end`)과 다르면 `success_differs_from_auto`가 켜진다. 자동으로 녹화를 끝내지는 않는다.

## 정지 구간 비율

로봇이 멈춰 있는 구간이 길면 학습에 나쁘다(손이 화면 밖이거나 망설이는 경우). **이웃한 두 샘플 사이에 `ctrl` 6개의 변화 중 가장 큰 값이 0.002 rad보다 작으면 "정지" 샘플**로 세고(`STILL_CTRL_DELTA_RAD`, 약 0.06 rad/s 미만), 정지 샘플 수 ÷ (샘플 수 − 1)를 `still_ratio`로 저장한다. 가장 긴 연속 정지는 `still_longest_s`. 집게만 움직여도 "움직임"으로 센다. 화면에는 녹화 중 실시간으로 나오고 마지막 저장본의 값도 보인다. 에피소드 시작 전 구간(손으로 조종을 시작하기 전)도 정지로 세므로 시작 직후 손을 바로 보이는 것이 좋다. 경고 기준(50%, 3초)은 임시이며 `web/src/record/config.js`.

## 측정 (실측)

`server/record_bench.py`(브라우저 없이 서버 객체를 직접 돌림, 손은 가짜 숫자). 서버 16코어 공용, 마지막 실행 2회분. **WebSocket 전송과 실제 브라우저는 들어 있지 않다.**

틱 간격(ms) = 시뮬레이션 스레드의 틱 시작 사이 벽시계 시간. 공칭 33.3ms. 화면이 있으면 렌더링 한 장(약 55ms)이 틱을 늘려서 최대가 40ms대가 되는 것은 원래 동작이다.

| 조건 | 평균 | 최대 | >40ms | >50ms | CPU(코어) |
|---|---|---|---|---|---|
| A 화면 없음, 녹화 없음 | 33.33 | 33.40 | 0 | 0 | 0.01 |
| D 화면 없음 + 녹화 30초 | 33.33 | 33.41 | 0 | 0 | 0.01 |
| B 화면 있음, 녹화 없음 | 33.34 | 46.92 | 105 | 0 | 1.68 |
| C 화면 있음 + 녹화 30초 (두 번째 실행) | 33.34 | 47.21 | 167 | 0 | 1.68 |
| E 화면 있음, 리셋만(녹화 없음) | 33.33 | 53.21 | 317 | 4 | 1.68 |

- **화면이 없을 때는 녹화 유무와 상관없이 틱 간격이 같고 CPU도 같다**(A와 D).
- 화면이 있을 때 첫 번째 실행에서 C의 최대(약 50ms)가 B(약 46ms)보다 컸다. 순서를 바꿔 다시 재니 **녹화가 없는 E가 53.2ms/317회로 더 나빴다.** 차이는 녹화가 아니라 그 시점의 시드 위치나 서버 상태를 따라가는 것으로 보이며 원인은 확인하지 않았다.
- 녹화 코드 자체의 비용은 직접 쟀다: `on_step` 한 번 평균 5.1µs, 틱당 0.034ms. 같은 프로세스에서 녹화를 켜고 끄며 번갈아 잰 12초 구간 4쌍의 최대 틱은 끔 44.2~44.7ms, 켬 44.3~46.9ms로 거의 같았다.
- 디스크 쓰기는 별도 스레드가 하고, 쓰기가 막혀도 틱이 계속 도는 것을 테스트로 확인했다(`test_blocked_disk_does_not_slow_the_tick_loop`).
- 샘플 간격: 900샘플/29.96초, 평균 33.33ms(최소 30, 최대 35ms), 격자 최대 오차 1.67ms.

## 학습·재생 카메라 (확인 결과)

`server/render.py`의 `StateRenderer`가 저장된 `qpos` 13개로 장면을 복원해 그린다. 설정은 `server/config.py`의 `RECORD_CAMERA_*`(방위각 110°, 고도 -35°, 거리 0.8m, 바라보는 점 `VIEW_LOOKAT_M`), 해상도 240×320(세로×가로, `RECORD_IMAGE_*_PX`), 그림자·반사는 실시간 화면과 같은 `RENDER_SHADOW`, `RENDER_REFLECTION`(둘 다 꺼짐)이다. 마우스로 돌리는 화면(`VIEW_*`)과 별개라서 화면을 돌려도 바뀌지 않는다(테스트로 확인).

`server/record_camera_check.py` 결과: 블록은 모든 모서리·자세에서 보이고 **약 13~15 × 15~19 px(면적 152~211 px)**, 목표(초록)도 보인다. 집게가 블록 높이까지 내려왔을 때 블록이 가장 많이 가려진 경우가 86%(14%가 가려짐)이고 나머지는 99~100%다. 이 숫자는 이미지를 직접 열어 보고도 확인했다. 단, **이 값은 시뮬레이션 화면 기준이고 학습이 잘 되는지는 아직 모른다.** 해상도·카메라 개수는 3-3 전에 최종 확정한다.

## 알려진 한계와 3-3에서 정할 것

- 저장에 실패한 에피소드는 사라진다(재시도 없음).
- 정지 구간 경고 기준(50%, 3초)은 임시다.
- 블록 방향(yaw)은 고정이다(회전 없음). 바꾸면 데이터 조건이 달라진다.
- 시드를 건너뛰는 경우가 있다(리셋만 하거나 취소). 시드 0~99 안에서 20개를 찍는 데는 충분하다.
- 화면 쪽 React 컴포넌트의 클릭·모양은 자동 테스트가 없다(DOM 테스트 도구 없음). 순수 로직은 테스트했고 실제 화면은 브라우저에서 직접 확인한다.
- 성공 20개만 쓸지 실패도 쓸지, 학습 해상도·카메라 개수(옆 카메라 추가 여부), `observation.state`를 qpos로 두는 것(이 문서의 규칙)은 3-3 시작 전에 확정한다.
- 서버와 웹을 내가 직접 띄워 본 결과(실제 브라우저에서의 틱 간격, 화면 모양)는 이 문서에 아직 없다.
