# 12. AUTO — 학습된 정책이 혼자 움직이기 (4-1)

화면 속 로봇이 학습된 ACT 1호(`checkpoints/dexter_act_v1/pretrained_model`)로 혼자 블록을 집어 목표에 놓는다. 4단계(교정 데이터 모으기)의 첫 조각이다.
손으로 넘겨받기(HUMAN)와 교정 녹화는 4-2에서 한다. **이 문서의 숫자는 이 서버에서 직접 실행해 얻은 값이다.** 측정 도구는 `server/auto_headless.py`.

## 구조

```
브라우저 ──ws──▶ server (server/.venv)                        정책 프로세스 (train/.venv, nice 19, 스레드 2)
                  app.py  ─ auto 메시지 ─▶ AutoRunner(auto.py)
                  SimWorker(시뮬레이션 스레드) ─ AutoEpisode ──Unix 소켓(/tmp, 0600)──▶ policy_server.py
                    · 샘플 격자(grid.py)에서 관측(StateRenderer) → 청크 요청        · evaluate.ActPolicy와 같은 로딩·전처리·후처리
                    · 청크를 큐에서 하나씩 ctrl에 그대로                              · 청크 = predict_action_chunk()[:, :n_action_steps]
                  ControlOwner(owner.py): IDLE / AUTO / HUMAN(4-2에서 켬)
```

| 파일 | 하는 일 |
|---|---|
| `server/auto_config.py` | AUTO 설정값 한 곳(체크포인트, 유휴 10분, 요청 제한 3초, 최대 45초 등). `server/config.py`는 건드리지 않았다 |
| `server/owner.py` | 제어 주체 상태(IDLE/AUTO/HUMAN). 한 순간에 ctrl을 쓰는 주체는 하나. 허용 전환은 IDLE↔AUTO뿐이고 HUMAN 전환은 자리만 있다 |
| `server/policy_ipc.py` | 소켓 메시지 형식 + `PolicyClient`(프로세스 띄우기/요청/유휴/끄기). stdlib와 numpy만 쓴다 |
| `server/auto.py` | `AutoEpisode`(한 에피소드의 루프), `AutoRunner`(명령 처리, 세션 횟수, 화면용 상태) |
| `server/sim_worker.py` | AUTO 훅(`start_auto`), 학습 카메라 렌더러 생성, 정책을 기다린 시간을 따라잡지 않는 시각 처리 |
| `server/control.py` | AUTO 중 손·키보드 입력 버리기, AUTO가 끝나면 마지막 ctrl 이어받기(`request_adopt`) |
| `server/recording.py` | AUTO 중 녹화·리셋 거절, AUTO 시작 조건(리셋 직후, 시연 시드)과 "리셋 직후" 표시 소비 |
| `train/policy_server.py` | 정책 프로세스. `evaluate.ActPolicy`를 상속해 청크를 낸다 |
| `server/auto_headless.py` | 브라우저 없이 라이브 루프를 돌려 평가와 비교, 측정, 고아 프로세스 확인 |
| `web/src/components/AutoPanel.jsx`, `web/src/auto/view.js` | "AUTO (학습된 정책)" 상자와 표시 규칙 |

## 실행 방법


정책 프로세스 전용 포트는 없다(Unix 소켓이라 VS Code Ports에 나타나지 않는다).

## 결정과 이유

### 소켓: Unix 소켓 (`/tmp/dexter-policy-<랜덤>/policy.sock`)
- 같은 서버에 46명이 로그인해 있다. `127.0.0.1` TCP는 누구나 접속할 수 있어서 남이 행동을 끼워 넣거나 프로세스를 멈출 수 있다.
- Unix 소켓은 0700 폴더 + 0600 파일이라 파일 권한이 접근 통제이고 포트 충돌도 없다. 테스트가 권한을 확인한다.
- 정책 프로세스가 모델을 다 읽은 **뒤에** 소켓을 열고, 서버가 접속해 READY를 받는다(소켓 파일이 보이면 곧 준비된 것).

### 청크 방식 (서버가 청크를 받아 큐에서 소비)
- `select_action`은 큐가 비었을 때만 `predict_action_chunk(...)[:, :n_action_steps]`를 부르고 나머지는 큐에서 꺼낸다(`lerobot/policies/act/modeling_act.py`).
  정책 프로세스는 같은 앞뒤 단계(`prepare_observation_for_inference` → 전처리 → 청크 → 후처리)로 청크를 낸다.
- **동치 확인(`train/tests/test_policy_server.py`)**: 샘플마다 `evaluate.ActPolicy.act`를 부른 결과(관측 2개, 청크 2개)와 청크 방식의 결과가
  **`np.array_equal`(비트까지 같음)**. 작은 체크포인트와 **실제 체크포인트(`dexter_act_v1`, 100개 × 2)** 모두 통과했다. 그래서 계획에 둔
  "같은 프로세스에서 `select_action`을 n번 부르는 방식"으로 **바꾸지 않았다**(그 방식도 `--chunk-mode loop`로 구현하고 같은 테스트를 통과시켜 두었다).
- 하나씩 방식은 샘플마다 소켓 왕복(초당 30번)이라, nice 19인 프로세스가 밀리면 시뮬레이션 틱이 그만큼 막힌다. 청크 방식은 약 3.3초마다 한 번이다.
- 시간 앙상블(`temporal_ensemble_coeff`) 체크포인트는 매 샘플 관측이 필요해서 정책 프로세스가 시작할 때 거부한다.

### 지연: 정책을 기다리는 동안 물리 시간을 멈춘다 (평가와 같음)
- 새 청크가 필요한 샘플(3.3초마다)에서 렌더링 + 요청 + 응답이 끝날 때까지 `mj_step`을 하지 않는다. 평가는 추론이 시간을 쓰지 않으므로 이렇게 해야 행동이 같다.
- 기다린 벽시계 시간을 따라잡느라 물리를 몰아서 돌지 않게, 기다린 뒤 시뮬레이션 시각 기준을 다시 잡는다(`sim_worker.py`).
  AUTO 중 한 틱에 따라잡는 상한은 `AUTO_CATCH_UP_S`(0.07초 = 화면 렌더링 틱 정도)로 줄인다. 테스트(`test_waiting_for_the_policy_does_not_burst_physics`)가
  0.25초 지연에서 시뮬레이션 시각이 한 번에 0.12초 넘게 뛰지 않는지 확인한다.
- 비동기로 미리 받는 방식(b)은 관측이 달라져 평가와 다른 행동이 나오므로 쓰지 않았다.
- 정책 요청 제한은 3초(`POLICY_REQUEST_TIMEOUT_S`). 넘으면 AUTO를 오류로 멈춘다. 기다리는 동안은 시뮬레이션 스레드가 막혀 화면과 중지 버튼도 멈춘다(정상은 약 0.1초).

### 시드와 시작 조건
- AUTO는 3-2의 **블록 리셋 버튼을 공유**한다. 리셋이 시연 시드를 순서대로 발급하므로(저장된 시연의 가장 큰 시드 + 1, 지금은 28부터) 학습에 쓴 시드(0~27)와 겹치지 않고
  사람 녹화와도 겹치지 않는다. 서버를 다시 켜면 AUTO가 썼지만 저장되지 않은 시드는 다시 나올 수 있다(괜찮다고 정함).
- **평가 시드(1000~1049)는 화면의 AUTO에서 막힌다**(리셋 버튼이 시연 시드만 내고, 시작 때 `seed_kind`를 한 번 더 확인한다). 헤드리스 검증은 내부 함수를 직접 불러 평가 시드로 돌린다.
- 시작하면 "리셋 직후" 표시가 꺼진다(녹화 시작과 같은 규칙). 끝나면 다시 리셋해야 한다.
- 팔이 home 자세에서 0.1 rad 넘게 벗어나 있으면(리셋 뒤 손으로 움직인 경우) 시작을 거절한다.
- 시작 자세는 리셋이 끝난 home(집게 열림)이고, 평가의 `EvalEnv.reset`처럼 데이터를 초기화하지는 않는다(화면 버튼 경로). `exact_start`(평가와 같은 초기화)는 검증용으로만 있고 버튼에는 연결하지 않았다.

### 정책 프로세스 수명
- AUTO 첫 시작 때 별도 스레드가 띄운다(서버 시작 때가 아니다). 로딩 중에는 `loading`, 화면에 "정책 불러오는 중, 약 N초".
- **끝난 뒤 유휴 10분 타이머가 시작된다**: AUTO가 끝나면 PING을 보내 프로세스의 유휴 시간을 0으로 되돌린다. 10분 동안 요청이 없으면 **정책 프로세스가 스스로 끝난다**(서버가 끄는 것이 아니다).
  화면에는 "정책 프로세스: 켜짐 (N초 후 종료) / 꺼짐"이 작게 보이고(서버가 남은 시간을 계산하므로 몇 초 어긋날 수 있다), **"정책 프로세스 지금 끄기"** 버튼이 `SHUTDOWN` 요청을 보낸다.
- 서버를 끌 때(lifespan 종료)도 정리한다. 프로세스가 죽거나 응답이 없으면 AUTO가 `error`로 멈추고(팔은 마지막 ctrl 유지) 화면에 오류가 뜬다. 서버는 계속 돈다. 다음 시작 때 프로세스를 다시 띄운다.
- 서버가 **kill -9로 죽어도** 정책 프로세스는 따라 죽는다(아래 "검증").

## 제어 주체
- `ControlOwner`가 IDLE / AUTO / HUMAN 하나를 가진다. 지금은 IDLE↔AUTO만 허용하고 HUMAN 전환(`FUTURE_TRANSITIONS`)은 이름만 있다(4-2).
- AUTO 중 `SimWorker`는 `ControlWorker`가 정한 ctrl을 `data.ctrl`에 쓰지 않고, `ControlWorker.tick`은 손·키보드 높이 입력을 쌓지 않고 버린다.
  테스트: `test_manual_ctrl_is_not_applied_while_auto_owns_the_robot`, `test_hand_and_height_input_is_dropped_while_auto_runs`.
- AUTO 중에는 녹화와 블록 리셋을 서버가 거절한다(이유 문구가 화면에 뜨고 `invalid_count`는 올라가지 않는다).
- AUTO가 끝나면 마지막 ctrl을 `SimWorker`와 `ControlWorker`에 같이 넘긴다(안 그러면 낡은 ctrl이 다시 적용되어 팔이 튄다). 전환 순간의 부드러움은 4-2에서 다시 본다.

## 프로토콜 (docs/04 외에 추가된 것)
- 브라우저 → 서버: `{"type":"auto","action":"start"|"stop"|"shutdown_policy"}`. 그 외 값과 다른 필드는 `ProtocolError`(연결 유지, `invalid_count` +1).
  형식은 맞지만 지금 못 하는 요청은 `error` 메시지로 이유를 돌려주고 `invalid_count`는 올리지 않는다.
- `state.auto`: `status`(idle, loading, running, success, timeout, stopped, error), `owner`, `seed`, `elapsed_s`, `max_s`, `sample`, `chunk_pos`, `chunk_len`,
  `last_latency_ms`(렌더+요청), `session_success`, `session_attempts`, `error`, `result`, `loading_s`, `load_estimate_s`, `policy`(`state` off/loading/on, `idle_remaining_s`), `last_event`.
- 세션 시도는 **성공과 시간 초과만** 센다(중지와 오류 제외). 파일 저장은 하지 않았다(제안: 나중에 `experiments/auto_sessions.csv`에 한 줄씩).

- AUTO는 실패 유형(집기 실패 등)을 나누지 않고 "시간 초과"로만 표시한다. 1000번은 평가에서 `grasp_fail`(블록이 안 들림)이다.

  첫 요청의 관측(state float32, 이미지)이 평가의 첫 관측과 같은 것도 같은 테스트에서 본다.

**live 시작**(화면과 같은 경로: 제어 스레드가 `BlockReset`으로 팔을 home에 올리고 블록을 놓은 직후 그 상태 그대로 시작, 화면 렌더링도 켬). 시드 1002, 1005, 1000:
세 시드 모두 위 표와 같은 결과다(1002 성공 13.535초 407샘플, 1005 성공 12.865초 387샘플, 1000 시간 초과 1351샘플, 블록 위치 차이 0.0004~0.0006 mm). 다만 접촉 물리가 아주 민감하다는 3-4의 관찰(ctrl 1e-6 rad만으로 결과가 갈림)이 있으므로
**3개 시드가 같았다는 것이 모든 시드에서 같다는 뜻은 아니다.**

- 화면이 없을 때 50ms를 넘는 틱은 **청크 요청 횟수와 같다**(1005: 요청 4번 → 4회, 1000: 14번 → 14회). 정책을 기다린 틱이다. 그 외 틱은 모두 40ms 이하다.
- 첫 에피소드(1002)의 최대 313~325ms는 학습 카메라 렌더러(EGL)를 처음 만드는 한 번의 비용이 더해진 것이다(요청 5번 + 이것 = 6회).
- 화면이 있을 때 >40ms가 많은 것은 화면 렌더링 틱(약 55ms)이라서 AUTO와 상관없는 3-2의 원래 동작이다. >50ms는 요청 횟수와 같거나 1회 많았다(1005는 4회=요청 4번, 1000은 15회 vs 요청 14번. 많은 1회의 원인은 확인하지 않았다).
- 평균이 33.3이 아니라 34~35인 것은 정책을 기다린 틱이 더해져서다. 시뮬레이션 시각은 멈췄다가 이어지므로 45초 에피소드가 벽시계로 약 47초 걸린다(1000번: 46.9~47.0초).

CPU와 메모리:

| | CPU(코어, 에피소드 평균) | 메모리(MB) |
|---|---|---|
| 서버(측정용 대역 프로세스, 화면 없음) | 0.03~0.06 | RSS 935 |
| 서버(측정용 대역, 화면 켬) | 1.66~1.69 (화면 JPEG 렌더링이 대부분. 3-2의 1.68코어와 같음) | RSS 1168 |
| 정책 프로세스 | 0.03~0.04 (nice 19, 스레드 2) | READY 직후 RSS 724, 요청 뒤 762, 최대(VmHWM) 920 |

- **정책 프로세스 메모리는 예상 약 1.9GB보다 훨씬 작다**(최대 0.92GB). "서버" 값은 실제 서버가 아니라 측정용 `auto_headless` 프로세스다(시뮬레이션 + 렌더러 2개, 웹소켓과 FastAPI는 없음).
- 정책 프로세스가 떠 있어도 놀고 있을 때는 CPU를 거의 쓰지 않고 메모리만 약 0.76GB 쓴다. 그래서 유휴 종료 타이머와 "지금 끄기"를 넣었다.

정책 프로세스 시작(프로세스 시작 → READY): **2.86, 2.46, 2.35초**(3번, 한가한 서버, 파일 캐시가 데워진 뒤). 앱 경로 전체(리셋 후 AUTO 시작 → 첫 샘플)는 2.8초였다. 화면 문구의 기본 N은 3초(`POLICY_LOAD_ESTIMATE_S`)이고 한 번 띄운 뒤에는 직전에 잰 값으로 바뀐다.
서버가 바쁘거나 파일 캐시가 비어 있으면 더 걸릴 수 있다(측정하지 않음).

### 3. 서버가 kill -9로 죽을 때 (`--mode orphan`)
서버 대역 프로세스가 정책 프로세스를 띄운 뒤 `SIGKILL`로 죽이고, 정책 프로세스가 사라지기까지를 쟀다:

| 상황 | 사라지기까지 | 소켓 폴더 |
|---|---|---|
| 연결된 상태(평소), 부모 감시 + 소켓 닫힘 | 0.66초 | 지워짐 |
| 연결된 상태, 소켓 닫힘만(부모 감시 끔) | 0.66초 | 지워짐 |
| 모델을 읽는 중(소켓이 아직 없음), 부모 감시 | 0.51, 0.56초 | 지워짐 |
| 모델을 읽는 중, 부모 감시 끔(기본 설정이 아님) | **안 사라짐**(60초 뒤에도 살아 있어 직접 끔) | 남음 |

- 평소에는 서버가 죽으면 커널이 소켓을 닫고, 정책 프로세스가 EOF를 읽어 끝난다. 모델을 읽는 중(약 2.5초)에는 소켓이 없어서 **부모 프로세스 번호가 바뀌는 것을 0.5초마다 확인**하는 감시가 대신한다(기본 설정에 켜져 있다).
- 첫 시험에서 부모 감시로 끝난 경우 **소켓 폴더가 남는 결함**을 찾아 고쳤다(`os._exit`가 정리 코드를 건너뛰었다). 고친 뒤 위 표의 값이 나왔다.
- 시험 뒤 `ps`로 `policy_server`/`auto_headless` 프로세스가 없고 `/tmp/dexter-policy-*` 폴더도 없음을 확인했다.

### 4. 테스트
- 서버: 새 테스트 59개 포함 682개 통과, 기존에 아는 실패 2개(`test_control_relative.py::test_app_default_mapper_follows_the_config_mode`, `test_mapping_relative.py::test_defaults_modes`, 작업 트리의 `MAPPING_MODE`가 "absolute"라서) 외 새 실패 없음.
- train: 52개 통과(새 15개: 청크 동일성, 소켓 프로토콜, 실제 프로세스 시작/종료/유휴/연결 끊김/시간 앙상블 거부).
- web: 216개 통과(새 테스트: AUTO 상자 표시 규칙, `sendAuto`).
- 가짜 정책 프로세스(진짜 소켓)로 확인한 것: 프로세스 사망, 늦은 응답, 오류 응답, 깨진 응답, 시작 실패, 시작 시간 초과, 로딩 중 취소, 시작/중지 반복, AUTO 중 다른 입력 무시, 정책을 기다리는 동안 물리가 몰아서 돌지 않음.

## 알려진 한계
- **라이브 = 평가는 확인한 시드(5개 exact, 3개 live)에서만 확인했다.** 접촉 물리가 민감해서 다른 시드에서 갈릴 수 있다(예: 화면 경로는 리셋 때 이전 접촉 기록이 남아 있다).
- 정책을 기다리는 동안(정상 약 0.1초, 최대 3초) 시뮬레이션 스레드가 막혀 화면 갱신과 중지가 늦는다.
- AUTO 중 `RobotPanel`의 일부 값(`ctrl_rad` 등)은 ControlWorker 기준이라 AUTO의 실제 ctrl과 다르게 보일 수 있다(손 입력이 없으므로 의미 없는 값).
- AUTO 시작 때 틱 간격 통계(`tick_stats`)를 초기화하므로 녹화 상자의 "틱 간격" 표시도 그 시점부터 다시 센다.
- 정책 프로세스가 `evaluate`를 import하므로 mujoco도 함께 불러온다(렌더링은 하지 않는다. 메모리에 포함된 수치).
- 유휴 타이머는 정책 프로세스 기준이고 화면 숫자는 서버가 계산한 값이라 몇 초 어긋날 수 있다.
- 파일 저장(세션 결과)은 하지 않았다. 4-2에서 교정 녹화와 함께 정한다.
- `docs/Handoff.md`, `docs/07-lerobot-notes.md`(11절 "정책 실행을 서버에 넣을 때 해결해야 한다")에 "4-1 완료, 정책은 별도 프로세스(Unix 소켓)로 해결"을 반영할 것 — 이 작업에서는 수정하지 않았다.
